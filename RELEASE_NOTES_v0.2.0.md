# Invokrum v0.2.0

Invokrum `v0.2.0` extends the deterministic local-composition baseline with an explicit distribution and authenticated local-installation boundary.

This is also the first version intended to be published from `hackelia-micrantha/invokrum-community`, the public source and release surface. The historical canonical `v0.1.0` tag remains bound to its original source commit; the later community baseline is not relabeled as `v0.1.0`.

## Highlights

- Canonical `invokrum.pack-bundle/v1` bundle identity and golden vectors.
- Provider-neutral publisher assertions and host-owned trust policy.
- Bounded local Linux directory and uncompressed POSIX ustar acquisition.
- Exact immutable-subject candidate verification before persistent installation.
- Strict `ed25519-subject-v1` publisher verification.
- Explicit host authorization kept separate from signature validity.
- Linux content-addressed installation through private quarantine.
- Deterministic unsigned `invokrum.installation/v1` and authenticated `invokrum.installation/v2` evidence.
- Operator-facing local directory/archive install workflows for digest-only and authenticated publisher claims.
- Independent subprocess reference-host coverage for capability negotiation, exact-byte persistence, verification, and drift blocking.

## Trust model

The release keeps distinct claims distinct:

1. bundle identity establishes the exact immutable subject;
2. candidate verification establishes that local bytes match that subject;
3. publisher verification establishes that signature evidence is valid for that subject;
4. host trust policy decides whether the verified publisher is authorized;
5. installation evidence records the resulting local provenance claim;
6. composition lock evidence records deterministic prompt composition separately.

A valid publisher signature is not host authorization, freshness, installation, or semantic prompt approval.

## Supported acquisition and installation

The supported secure installation path is Linux-local:

- already-local directory candidates;
- bounded uncompressed POSIX ustar candidates;
- digest-only installation with explicit expected immutable subject;
- authenticated Ed25519 installation with independently supplied verification material and host-owned trust policy;
- Linux XDG store-root resolution for the operator CLI.

The archive adapter does not extract arbitrary filesystem objects. It maps the supported bounded ustar profile into owned candidate bytes before ordinary exact verification and installation.

## Public repository transition

`hackelia-micrantha/invokrum-community` is the public distribution, contribution, and release repository. Shared changes are promoted from the separately maintained canonical repository through reviewed, allowlisted source selection with explicit provenance; private Git history is not mirrored.

The initial community baseline was selected from canonical commit `0e6083d0608d22673b7172ce3330328c64be05bc`. Repository-specific relocation differences are recorded in `UPSTREAM.md` in the community repository.

## Release artifacts

The release pipeline produces prerelease archives for:

- `x86_64-unknown-linux-gnu`;
- `x86_64-apple-darwin`;
- `x86_64-pc-windows-msvc`.

Each archive is accompanied by a SHA-256 checksum and SPDX 2.3 SBOM, with GitHub provenance and SBOM attestations generated by the release workflow.

macOS and Windows binaries support portable operations. Secure filesystem-backed acquisition/installation remains Linux-specific and unsupported platform paths fail closed.

## Security limitations

`v0.2.0` does not provide:

- remote or HTTPS acquisition;
- registry discovery;
- freshness, expiry, revocation, transparency, or rollback/freeze selection policy;
- production publisher private-key custody or signing-key discovery;
- prompt semantic safety analysis;
- runtime tool/network sandboxing or authorization.

Mutable aliases such as branches, floating tags, or `latest` are not final security identities.

## Upgrade and compatibility

Invokrum remains pre-1.0. Public schema, lock, bundle, installation-evidence, CLI machine-output, host RPC, and Rust API contracts are versioned independently where required. Hosts should reject unsupported identifiers rather than infer compatibility.

Existing `invokrum.lock/v1` composition evidence remains a separate contract from bundle, publisher, and installation evidence.
